Sniffy inspects HTTPS traffic using a man-in-the-middle (MITM) proxy. The client establishes a TLS connection to Sniffy, which opens a separate TLS connection to the destination server. The client must trust Sniffy's root certificate to accept the certificates it signs for destination hosts.

Before using HTTPS decryption:

- Install and trust the root certificate on the clients you want to debug. Clients that verify certificates reject intercepted connections if they do not trust it.
- The root certificate's private key stays on your machine (`certificates/` in the configuration directory, mode `0700`). Anyone who obtains it can issue certificates for any domain that your machine will trust. **Don't share it.**

## Installing the root certificate

<Screenshot src="certs-overview.png" alt="The Certificates screen: root certificate status, download button, and platform switcher" caption="The Certificates screen" />

On first launch Sniffy generates `certificates/sniffy-ca.crt` and `sniffy-ca.key` in the configuration directory. Open the **Certificates** screen and follow the guide for your platform.

### macOS

Click "Install to This Machine" and confirm the system authorization prompt. The certificate goes into **your login keychain** and is marked as a trusted root.

The trust setting applies to the current user. On a shared machine, install the certificate separately for each user who needs it.

To install manually, download the `.crt` and double-click it to import it into Keychain Access. Open Sniffy Root CA, expand "Trust", and set "When using this certificate" to "Always Trust". Close the window and enter your password to confirm.

### Windows

Click "Install to This Machine" and approve the UAC prompt. The certificate goes into the local machine's "Trusted Root Certification Authorities" store.

Manual install: download the `.crt`, double-click it - Install Certificate - store location "Local Machine" - place it in "Trusted Root Certification Authorities" - Finish. Restart your browser afterwards.

### Linux

"Install to This Machine" uses `pkexec` to gain root privileges, copies the certificate into your distribution's CA anchor directory, and rebuilds the trust store:

| Distribution            | Anchor directory                            | Rebuild command           |
| ----------------------- | ------------------------------------------- | ------------------------- |
| Debian / Ubuntu         | `/usr/local/share/ca-certificates`          | `update-ca-certificates`  |
| RHEL / Fedora / CentOS  | `/etc/pki/ca-trust/source/anchors`          | `update-ca-trust extract` |
| Arch / Manjaro          | `/etc/ca-certificates/trust-source/anchors` | `update-ca-trust extract` |
| openSUSE                | `/etc/pki/trust/anchors`                    | `update-ca-certificates`  |

Some Linux browsers use separate NSS certificate stores. Installation attempts to update `~/.pki/nssdb` and `cert9.db` in each Firefox profile. If `certutil` is missing (`libnss3-tools` on Debian-based systems) or a database is locked, this step may be skipped. Import the certificate manually in the browser settings if needed.

If `pkexec` is unavailable, install manually using the table above. On other distributions, add the Sniffy root using whatever certificate management tools they provide.

### iOS / Android

The device needs to be on the same network as your machine and have its Wi-Fi proxy pointed at your LAN address. The Certificates screen has step-by-step guides for both systems, including a QR code for the iOS profile download. Full walkthrough in [Phones and remote clients](/en/docs/mobile/).

## Scoping decryption

<Screenshot src="settings-decrypt-scope.png" alt="HTTPS decryption in Settings: the scope selector and the allowlist field" caption="HTTPS decryption scope" />

By default every host is decrypted. You can narrow this under Settings - HTTPS Decryption. Hosts outside the scope pass through as CONNECT tunnels: you still see the destination host and byte counts, but not the content.

| Scope           | Behavior                                   |
| --------------- | ------------------------------------------ |
| All Hosts       | Decrypt everything                         |
| Allowlist Only  | Decrypt only listed hosts, tunnel the rest |
| Except Denylist | Tunnel listed hosts, decrypt the rest      |

Enter one host per line. `*` wildcards are supported: `*.example.com` matches both the bare domain `example.com` and its subdomains.

Narrowing the scope is the first thing to try when:

- An app uses **certificate pinning**. Add its domains to the denylist so they are forwarded through a tunnel.
- The traffic involves banking, payments, or corporate SSO, and you don't want it stored in plaintext in the capture log.
- You only need to decrypt a few specific domains. List them in the allowlist.

Turning off "Enable HTTPS MITM" disables decryption entirely; every HTTPS connection becomes a tunnel.

## Importing and exporting the root certificate

**Export** lets you use the same root certificate on another device or in another tool. The Certificates screen offers PEM, CRT, DER, and PKCS#12. PKCS#12 includes the private key, so you must set a password.

**Import** switches Sniffy to an existing CA, such as a test CA shared by your team. PEM bundles and password-protected PKCS#12 files are supported. The imported CA takes effect immediately without a restart. Clients must trust it.

**Regenerate** replaces the root certificate and private key that Sniffy uses. Client devices keep trusting the old certificate until you remove it, so on each client, install and trust the new certificate, remove the old one, and restart the browser.

## Server certificates for specific domains

On the Certificates screen, use "Import Server Certificate" to add a domain's certificate and private key. Sniffy presents that certificate to clients connecting to matching hosts. Clients must trust its issuer chain, and the certificate must pass hostname, validity, and other verification checks.

Matching hosts are read from the certificate's SAN, falling back to CN when SAN is absent. Certificates and private keys are stored in `servercerts.json` in the configuration directory.

## Outbound certificate verification

When connecting to an upstream server, Sniffy verifies the certificate chain, hostname, and validity period by default. Verification failures stop forwarding and are recorded as errors.

Trusting Sniffy's root on a client only makes that client accept certificates signed by Sniffy. It does not make Sniffy accept arbitrary origin certificates.

If an internal test environment uses self-signed certificates, import the origin CA into the trust store of the system running Sniffy, then restart Sniffy. To skip verification temporarily, list the specific hosts in `config.json` in the configuration directory (its location is given in the [Configuration reference](/en/docs/configuration/)):

```json
{
  "tlsInsecureHosts": ["dev.example.test", "127.0.0.1"]
}
```

The list is empty by default. Entries must be exact hostnames or IPs — no ports, URLs, or wildcards — and subdomains are not matched. Quit Sniffy before editing the file by hand.

To change the list while Sniffy is running, use the management API (see the [Management API reference](/en/docs/api/config/)). Changes apply to new requests. Established long-lived connections, such as WSS, must reconnect.

## Removing the root certificate

When you stop using Sniffy, remove its root certificate from your devices' trust stores and delete the locally stored private key.

- **macOS** — open Keychain Access, find Sniffy Root CA in the login keychain, and delete it.
- **Windows** — run `certmgr.msc` (or `certlm.msc` for the local machine store) and delete Sniffy Root CA under Trusted Root Certification Authorities - Certificates.
- **Linux** — delete `sniffy-ca.crt` from the anchor directory and re-run your distribution's rebuild command. For browser NSS databases, remove the certificate separately in the browser's certificate settings.
- **iOS** — go to Settings - General - VPN & Device Management and remove the profile.
- **Android** — go to Settings - Security - Encryption & credentials - User credentials and remove the certificate.

Then delete the `certificates/` directory from the configuration directory.

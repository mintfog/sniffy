Use breakpoints when you want to edit a single request, see how an API handles invalid parameters, or swap in a different response while reproducing an issue. A breakpoint holds traffic before the request reaches the upstream server or before the response reaches the client, so you can inspect and edit it, then resume or abort it.

Open the **Breakpoints** screen (`Alt+B`).

## Two ways to trigger

<Screenshot src="breakpoints-overview.png" alt="The Breakpoints screen: global switches, URL rule list, and paused requests" caption="The Breakpoints screen" />

### Global breakpoints

Two switches, each covering **all** traffic in one phase:

- **Request breakpoint** — pause before the request goes upstream; you can change the method, URL, headers, and body.
- **Response breakpoint** — pause before the response reaches the client; you can change the status code, status text, headers, and body.

Global breakpoints pause all traffic in the selected phase. Opening a web page may produce many paused entries at once. Use **Resume all** or **Abort all** to handle them together.

### Breakpoint rules

Scoping by URL is the more common choice. Under "Breakpoint rules", click "Add Rule", enter a URL pattern, and tick the phases to intercept:

- Without `*`, the pattern matches as a **substring**: `/api/pay` catches any URL containing it.
- With `*`, the pattern matches the **whole URL**: `https://api.example.com/*/orders` must match end to end, with `*` standing in for any characters. Characters such as `.`, `?`, and `+` in the pattern match literally.

Each rule can be enabled, disabled, or deleted individually. Global switches and rules combine with OR: if either matches, the flow pauses.

## Handling paused requests

Matching flows appear in the "Paused requests" list, each labeled with its phase and a countdown.

| Action                         | Effect                                                   |
| ------------------------------ | -------------------------------------------------------- |
| **Resume unchanged**           | Continue without changes                                 |
| **Edit**                       | Open the editor, then continue with "Resume with edits"  |
| **Abort**                      | End the flow; the client sees the connection reset       |
| **Extend**                     | Restart the countdown, for edits that take longer        |
| **Resume all** / **Abort all** | Handle everything in the list at once                    |

### Timeouts resume automatically

Each paused entry has a default deadline of **5 minutes**. When it runs out, the entry resumes unchanged, any edits you have not submitted are dropped, and the list shows that it timed out.

Up to **100 flows** can be paused at once. Once the limit is reached, new flows skip the breakpoint and continue processing.

## The editor

<Screenshot src="breakpoints-editor.png" alt="The breakpoint editor with headers and body tabs, and release and abort buttons below" caption="The breakpoint editor" />

"Edit and resume" has tabs for headers and body.

On the request side you can change the **method**, **URL**, headers, and body; on the response side, the **status code**, **reason phrase**, headers, and body. The body editor has a "Format JSON" button, and lengths are recomputed from the new content when the flow resumes.

A few kinds of body are not loaded into the editor. The editor says why and keeps them as-is on resume:

| Case                   | Reason                                                                 |
| ---------------------- | ---------------------------------------------------------------------- |
| The body isn't text    | Binary content loses bytes on a round trip through a text editor       |
| Over the editing limit | The limit is 2 MiB; larger bodies aren't read in whole                 |
| Pass-through response  | The body is forwarded as it arrives and is not loaded into the editor  |
| Streaming response     | The body is relayed message by message from upstream                   |

In the last two cases **the status line and response headers remain editable and do take effect**; only the body is off limits.

Some headers, such as `Content-Length`, are recalculated from the final message when sent. The editor marks these fields; manual edits do not override the calculated values.

Closing the editor discards all your edits to that request, but the request stays held at the breakpoint until you decide what to do with it. Closing the editor does not resume it.

## How breakpoints relate to rules and plugins

Breakpoints work alongside rules and plugins. A rewritten flow can still pause at a breakpoint. After it resumes, the action already chosen by a rule or plugin (continue, mock, or abort) still applies.

Plugins can also trigger breakpoints by calling `setBreakpoint()` in `onRequest` or `onResponse`, so only flows that meet a complex condition stop and wait for you. See [JavaScript plugins](/en/docs/plugins/).

## Breakpoints in headless mode

The management API covers the whole feature. A match pushes a `breakpoint_hit` event over `/api/ws`, and resolution pushes `breakpoint_resolved`.

```bash
# Turn on the global request breakpoint
curl -X PUT http://127.0.0.1:8888/api/breakpoints/global \
  -H "Authorization: Bearer $SNIFFY_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"onRequest": true, "onResponse": false}'

# List paused entries
curl http://127.0.0.1:8888/api/breakpoints \
  -H "Authorization: Bearer $SNIFFY_API_TOKEN"

# Resume with edits
curl -X POST http://127.0.0.1:8888/api/breakpoints/{id}/resume \
  -H "Authorization: Bearer $SNIFFY_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"request": {"headers": [["X-Debug", "1"]], "body": "{}"}}'

# Resume unchanged
curl -X POST http://127.0.0.1:8888/api/breakpoints/{id}/resume \
  -H "Authorization: Bearer $SNIFFY_API_TOKEN"
```

The resume request body is an edit patch: include only the fields to change. Omit `headers` or set it to `null` to keep existing headers; an array replaces them, and `[]` clears them. Unknown fields return 400. Use the patch schema: bodies in paused snapshots use base64, while patch `body` fields contain text.

See the [Management API reference](/en/docs/api/breakpoints/) for all endpoints.

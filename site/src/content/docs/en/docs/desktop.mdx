This page takes you from a fresh install to reading and changing HTTPS traffic: launch the app, route traffic through it, trust the root certificate, inspect a session, and edit a request. Each step links to the page that covers it in depth.

## 1. Launch

<Screenshot src="workbench-overview.png" alt="The Sniffy desktop window: proxy bar on top, icon rail on the left, traffic list in the middle" caption="The desktop app" />

Install the app (see [Installation](/en/docs/install/)) and start it. The proxy bar across the top shows the current state:

- **Listening `:8080`** — the proxy is bound to this port. You can change it under Settings - Proxy, but the new port only applies after you restart the app.
- **System proxy on / off** — whether your machine's HTTP/HTTPS proxy currently points at Sniffy.
- **Pause / Resume** — pausing stops recording new traffic and nothing else. The port stays bound and open connections keep working.

The icon rail on the left switches between six screens: Traffic, Rewrite Rules, Breakpoints, Plugins, Certificates, and Settings.

## 2. Route traffic to Sniffy

Click **Enable system proxy** in the proxy bar. Sniffy sets itself as the system HTTP/HTTPS proxy, and apps that honor the system proxy start sending their requests through it.

If you only want one program's traffic, or that program ignores the system proxy, set its HTTP / HTTPS proxy to `127.0.0.1:8080` yourself. For a phone or another machine, use this machine's LAN address instead; the network menu in the proxy bar lists the address of each interface.

SOCKS5, upstream proxies, proxy authentication, and throttling are covered in [Routing traffic](/en/docs/capture/).

Open an `http://` page and check that it shows up in the traffic list. HTTPS requests will appear too, but you can't read their contents until the client trusts the root certificate.

## 3. Trust the root certificate

<Screenshot src="certs-install.png" alt="The Certificates screen showing the guide for the current platform and the Install to This Machine button" caption="The certificate installation guide" />

Sniffy decrypts HTTPS by presenting its own certificates, so the client has to trust Sniffy's root certificate. Open the **Certificates** screen:

- **macOS / Windows** — click **Install to This Machine**. Sniffy adds the certificate to the trust store with the system's own tools, so expect an authorization prompt. You can also download the `.crt` and follow the manual steps on the page.
- **Linux** — click **Install to This Machine** and authorize through `pkexec` to add the certificate to the system trust store. Sniffy also tries to add it to the current user's browser NSS databases; if the browser still shows a certificate error, import it there by hand.
- **iOS / Android** — switch to that platform's guide and follow its steps to set the Wi-Fi proxy and install the certificate.

Restart your browser and load an HTTPS site again. The traffic list now shows the decrypted requests and responses.

[HTTPS and the root certificate](/en/docs/https/) explains how the certificates work, how to limit which hosts get decrypted, and why certificate pinning makes some clients fail.

## 4. Inspect your first session

<Screenshot src="workbench-detail-panel.png" alt="The detail panel showing a request above its response, with overview, params, headers, body and raw tabs" caption="The session detail panel" />

The traffic list adds one row per request in the order they arrive, with the newest at the bottom. Columns show method, URL, status, duration, size, originating process, and client IP.

- The search box at the top (`Ctrl+F`) filters by URL, host, method, status code, and process name.
- The quick filters next to it show only errors or only images.
- **Follow Latest** keeps the list scrolled to the bottom as new rows arrive. Scrolling up turns it off.

Click a row to open the detail panel. The request is on top, the response below:

| Tab                      | Contents                                                          |
| ------------------------ | ----------------------------------------------------------------- |
| Overview                 | Method, scheme, status, duration, size, client IP, process        |
| Params                   | Query parameters and form fields                                  |
| Request / Response headers | Header table; click a key or value to copy it                   |
| Request / Response body  | Rendered by content type as a JSON tree, text, or hex; images, audio, and video preview inline |
| Raw                      | The message text, unformatted                                     |

`Ctrl+F` inside the detail panel searches the current session. You can limit the search to Request, Response, or Content.

The right-click menu on a row lets you copy the URL or a cURL command, highlight the row in a color, mark it read or unread, delete it, or resend it. [The workbench](/en/docs/workbench/) covers the rest of the interface.

## 5. Change one request

There are four ways to change traffic. They differ in whether the change runs automatically and whether you need to write logic:

| Approach            | Use it when                                                 | Docs                                     |
| ------------------- | ----------------------------------------------------------- | ---------------------------------------- |
| Request composer | You want to edit and resend a captured request, or build one from scratch | [Request composer](/en/docs/compose/) |
| Rewrite rules | A fixed condition should trigger the same change every time, with no code | [Rewrite rules](/en/docs/rules/) |
| Breakpoints | You want to hold matching traffic, check and edit it by hand, then let it through | [Breakpoints](/en/docs/breakpoints/) |
| JavaScript plugins | You need branching logic, computed signatures, or state shared across requests | [JavaScript plugins](/en/docs/plugins/) |

The quickest to try is the composer. Right-click a request in the traffic list and choose **Edit and Resend**. The composer opens with that request's method, URL, and headers, plus its body ready to edit. Send it, and a new session appears in the traffic list marked as a resend.

Rules and plugins change traffic without you stepping in. For example, this plugin catches requests to `/api/profile` and answers them with a mock response:

```js
function onRequest(flow) {
  if (flow.path !== "/api/profile") return;

  mock({
    status: 200,
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ name: "Sniffy", plan: "pro" }),
  });
}
```

To try it, create a plugin on the **Plugins** screen, paste the script, save, and enable it.
